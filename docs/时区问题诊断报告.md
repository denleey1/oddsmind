# 时区问题诊断报告

## 🔍 问题描述

用户反馈：校验 `expires_at` 时虽然把 datetime 统一为 UTC，但数据库里保存的值如果直接用本地时间查看，往往会被误认为"到当天结束才失效"。

例如：
- 服务器在 UTC+0，用户在 UTC+8
- 20 日 03:00 激活，过期时间实际上是 21 日 03:00（UTC）
- 换算成本地时间就是 21 日 11:00
- 肉眼看起来像"21 日上午还没失效"

---

## 📋 需要确认的问题

### 1. 数据库存储的时区

**问题**：数据库里 `expires_at` 是什么时间，标注的是哪个时区？

**需要检查**：
- MySQL 全局时区设置：`SELECT @@global.time_zone;`
- MySQL 会话时区设置：`SELECT @@session.time_zone;`
- 数据库中的实际值：`SELECT expires_at FROM miniprogram_users LIMIT 1;`
- MySQL 的 `NOW()` 返回什么时区？

### 2. 服务器时区设置

**问题**：服务器 `datetime.now()` 和数据库 session 的 `time_zone` 是否统一？

**需要检查**：
- Python `datetime.now()` 返回的时区
- 数据库连接时设置的会话时区
- 两者是否一致

## 🔎 代码检查结果

### 1. 写入逻辑（utils/miniprogram_db.py）

#### 位置1：`activate_user()` 函数（第86行）
```python
expires_at = datetime.now() + timedelta(days=expires_days)
```
- **问题**：使用 `datetime.now()`，返回**本地时间**（CST，UTC+8）
- **存储**：直接存储到数据库，无时区信息

#### 位置2：`activate_user_with_invite_code_atomic()` 函数（第326行）
```python
account_expires_at = datetime.now() + timedelta(days=expires_days)
```
- **问题**：同样使用 `datetime.now()`，返回**本地时间**

#### 位置3：SQL 中的 `NOW()` 函数
```sql
activated_at = NOW(),
last_login_at = NOW()
```
- **问题**：`NOW()` 返回的是**数据库会话时区**的时间

### 2. 数据库会话时区设置（app_database.py）

#### 位置：`execute_query()` 和 `execute_update()`（第30-36行，第63-69行）
```python
import time
tz_offset = time.strftime('%z')
tz_offset_formatted = f"{tz_offset[:3]}:{tz_offset[3:]}"
cursor.execute(f"SET time_zone = '{tz_offset_formatted}'")
```
- **当前行为**：设置为**系统时区**（CST，+08:00）
- **影响**：`NOW()` 返回 CST 时间

### 3. 读取逻辑（auth.py, miniprogram.py）

#### 位置1：`auth.py` 第121行
```python
if isinstance(expires_at, datetime) and expires_at.tzinfo is None:
    expires_at = expires_at.replace(tzinfo=timezone.utc)
```
- **假设**：数据库存储的是 UTC 时间
- **问题**：实际存储的是 CST 时间（UTC+8）

#### 位置2：`application/routes/miniprogram.py` 第198行
```python
elif isinstance(expires_at, datetime) and expires_at.tzinfo is None:
    expires_at = expires_at.replace(tzinfo=timezone.utc)
```
- **同样假设**：数据库存储的是 UTC 时间

## ⚠️ 问题分析

### 时区不一致的根源

1. **写入时**：
   - Python 代码：`datetime.now()` → CST (UTC+8)
   - SQL 函数：`NOW()` → CST (因为会话时区设置为 +08:00)
   - **结果**：数据库存储的是 CST 时间，但**没有时区信息**

2. **读取时**：
   - 代码假设：数据库存储的是 UTC
   - 实际存储：CST (UTC+8)
   - **结果**：读取时添加 `timezone.utc`，导致**8小时误差**

### 具体影响示例

**场景**：用户在 2025-11-20 03:00 (CST) 激活，有效期 1 天

1. **写入数据库**：
   ```python
   expires_at = datetime.now() + timedelta(days=1)
   # 结果：2025-11-21 03:00 (CST，无时区信息)
   # 存储：2025-11-21 03:00 (MySQL 认为是服务器时区 CST)
   ```

2. **读取并比较**：
   ```python
   # 代码假设是 UTC
   expires_at = expires_at.replace(tzinfo=timezone.utc)
   # 结果：2025-11-21 03:00 UTC
   
   now_utc = datetime.now(timezone.utc)
   # 结果：2025-11-21 05:13 UTC (实际当前时间)
   
   if expires_at < now_utc:  # 2025-11-21 03:00 < 2025-11-21 05:13
       # 误判为已过期！
   ```

3. **实际情况**：
   - 存储：2025-11-21 03:00 CST = 2025-11-20 19:00 UTC
   - 应该比较：2025-11-20 19:00 UTC < 2025-11-21 05:13 UTC ✅ 已过期
   - 但代码比较：2025-11-21 03:00 UTC < 2025-11-21 05:13 UTC ❌ 误判

## 🔍 需要确认的具体信息

### 1. 数据库时区设置

请执行以下 SQL 查询：

```sql
-- 1. 全局时区
SELECT @@global.time_zone;

-- 2. 会话时区
SELECT @@session.time_zone;

-- 3. 当前时间对比
SELECT 
    NOW() as now_local,
    UTC_TIMESTAMP() as now_utc,
    CONVERT_TZ(NOW(), @@session.time_zone, '+00:00') as now_utc_converted;

-- 4. 查看实际存储的值
SELECT 
    id,
    openid,
    expires_at,
    activated_at,
    CONVERT_TZ(expires_at, @@session.time_zone, '+00:00') as expires_at_utc
FROM miniprogram_users 
WHERE expires_at IS NOT NULL 
LIMIT 5;
```

### 2. Python 系统时区

```python
from datetime import datetime, timezone
import time

print(f"datetime.now(): {datetime.now()}")
print(f"datetime.now(timezone.utc): {datetime.now(timezone.utc)}")
print(f"系统时区: {datetime.now().astimezone().tzinfo}")
print(f"时区偏移: {time.strftime('%z')}")
```

### 3. 数据库连接时的时区设置

检查 `app_database.py` 中设置的时区是否与系统时区一致。

## 📝 总结

**核心问题**：
1. ✅ **写入时**：使用本地时间（CST），存储到数据库
2. ✅ **数据库会话**：设置为系统时区（CST）
3. ✅ **读取时**：假设是 UTC，添加 `timezone.utc`
4. ❌ **结果**：8小时时差导致过期判断错误

**需要确认**：
- [ ] 数据库全局时区设置
- [ ] 数据库会话时区设置（app_database.py 设置的）
- [ ] 数据库中的实际存储值
- [ ] 服务器系统时区

**修复方向**（待确认后）：
- 方案1：统一使用 UTC（推荐）
- 方案2：统一使用本地时区（不推荐，跨时区部署有问题）
