## 🔴 严重漏洞（Critical）

### 1. ❌ 登录接口未验证过期时间的时区问题

**位置：** `application/routes/miniprogram.py:186-189`

```python
if isinstance(expires_at, str):
    expires_at = datetime.fromisoformat(expires_at.replace('Z', '+00:00'))
if expires_at < datetime.now()  # ← 问题：datetime.now() 是本地时间，可能与数据库时区不一致
```

**问题：**
- 数据库存储的是什么时区？
- `datetime.now()` 获取的是服务器本地时间
- 如果数据库存储 UTC 但比较用本地时间，会导致时区错乱
- **可能导致：** 已过期账号仍能登录，或未过期账号被拒绝

**影响：** 🔴 高危 - 账号过期验证失效

**修复建议：**
```python
# 统一使用 UTC 时间
if isinstance(expires_at, str):
    expires_at = datetime.fromisoformat(expires_at.replace('Z', '+00:00'))
elif isinstance(expires_at, datetime) and expires_at.tzinfo is None:
    # 假设数据库存储的是 UTC 时间
    expires_at = expires_at.replace(tzinfo=timezone.utc)

now = datetime.now(timezone.utc)
if expires_at < now:
    return api_error("账号已过期，请联系管理员", status=403)
```

### 3. ❌ 激活用户时未检查用户是否已过期后重新激活

**位置：** `utils/miniprogram_db.py:328-335`

```python
cursor.execute("""
    UPDATE miniprogram_users
    SET is_activated = TRUE,
        activated_at = NOW(),
        expires_at = %s,
        invite_code_used = %s
    WHERE openid = %s
""", (account_expires_at, invite_code, openid))
```

**问题：**
- 激活条件只检查 openid，没有检查 `is_activated` 状态
- 虽然应用层在第 290 行拒绝了已激活用户，但数据库层没有约束
- **如果有人直接调用 `activate_user_with_invite_code_atomic`，可以绕过应用层检查**

**场景：**
```python
# 恶意代码直接调用底层函数
activate_user_with_invite_code_atomic(
    openid="已激活用户的openid",
    invite_code="另一个激活码",
    expires_days=365,
    user_id=user_id
)
# ✅ 成功！用户被重新激活，过期时间被延长，激活码被消耗
```

**影响：** 🔴 高危 - 已激活用户可以重复使用激活码延长有效期

**修复建议：**
```python
cursor.execute("""
    UPDATE miniprogram_users
    SET is_activated = TRUE,
        activated_at = NOW(),
        expires_at = %s,
        invite_code_used = %s
    WHERE openid = %s
      AND is_activated = FALSE  -- ← 只激活未激活的用户
""", (account_expires_at, invite_code, openid))

if cursor.rowcount == 0:
    # 检查用户是否已激活
    cursor.execute("SELECT is_activated FROM miniprogram_users WHERE openid = %s", (openid,))
    user_info = cursor.fetchone()
    if user_info and user_info['is_activated']:
        conn.rollback()
        return False, "用户已激活，不能重复激活"
    else:
        conn.rollback()
        return False, "用户不存在"
```

### 5. ⚠️ 没有限制微信 code 的重复使用

**位置：** `application/routes/miniprogram.py:144` 和 `271`

```python
wechat_data = get_openid_from_wechat(code)
```

**问题：**
- 微信的 code 是一次性的，使用后应该失效
- 但代码没有记录已使用的 code
- **攻击者可以重放 code 进行登录/激活**

**场景：**
1. 攻击者拦截受害者的 code
2. 攻击者使用该 code 调用激活接口
3. 如果微信 API 还未使 code 失效，攻击者可以消耗受害者的激活码

**影响：** 🟠 中危 - 重放攻击风险

**修复建议：**
```python
# 1. 记录已使用的 code（使用 Redis，5分钟过期）
def check_and_mark_code_used(code: str) -> bool:
    """检查 code 是否已使用，如果未使用则标记为已使用"""
    import redis
    r = redis.Redis()
    key = f"wx_code_used:{code}"
    if r.exists(key):
        return False  # 已使用
    r.setex(key, 300, "1")  # 5分钟过期
    return True

# 2. 在调用微信 API 前检查
if not check_and_mark_code_used(code):
    return api_error("code 已被使用", status=400)
wechat_data = get_openid_from_wechat(code)
```

### 6. ⚠️ 数据库连接池的事务管理不完善

**位置：** `utils/miniprogram_db.py:257-366`

```python
try:
    cursor = conn.cursor()
    cursor.execute("START TRANSACTION")
    # ...
finally:
    if cursor:
        cursor.close()
    if conn:
        conn.close()  # ← 归还连接池
```

**问题：**
- 使用连接池时，`conn.close()` 是归还连接，不是真正关闭
- 如果发生异常但没有正确回滚，连接可能处于未知状态
- `finally` 块中的 `conn.close()` 在 `try` 块中也有，可能重复关闭

**影响：** 🟠 中危 - 连接池污染、事务泄露

**修复建议：**
```python
conn = None
cursor = None
try:
    conn = get_connection()
    cursor = conn.cursor()
    cursor.execute("START TRANSACTION")
    
    # ... 业务逻辑 ...
    
    conn.commit()
    return True, None
    
except Exception as e:
    if conn:
        try:
            conn.rollback()
        except:
            pass
    logger.error(f"原子性激活失败: {e}", exc_info=True)
    return False, f"激活失败: {str(e)}"
    
finally:
    if cursor:
        try:
            cursor.close()
        except:
            pass
    if conn:
        try:
            conn.close()
        except:
            pass
```

### 9. ⚠️ JWT Token 的 expires_at 和 exp 可能不一致

**位置：** `utils/jwt_helper.py:30-65`

```python
# Token 过期时间（从当前时间开始计算）
exp = datetime.utcnow() + timedelta(days=JWT_EXPIRATION_DAYS)

# 构建 payload
payload = {
    'expires_at': user_data.get('expires_at'),  # 账号过期时间（可能是 2025-11-17）
    'exp': exp  # Token 过期时间（7天后）
}
```

**问题：**
- 如果账号有效期是 1 天（明天过期），但 Token 有效期是 7 天
- Token 在第 2-7 天仍然有效，但账号已过期
- **虽然代码有检查 `expires_at`，但这增加了复杂度和出错风险**

**影响：** 🟡 中危 - Token 有效期管理混乱

**修复建议：**
```python
# Token 过期时间应该取 min(账号过期时间, 7天后)
account_expires_at_str = user_data.get('expires_at')
if account_expires_at_str:
    account_expires_at = datetime.fromisoformat(account_expires_at_str.replace('Z', '+00:00'))
    token_max_exp = datetime.utcnow() + timedelta(days=JWT_EXPIRATION_DAYS)
    exp = min(account_expires_at, token_max_exp)
else:
    exp = datetime.utcnow() + timedelta(days=JWT_EXPIRATION_DAYS)
```

## 📊 数据库层面的问题

### 17. ❌ 缺少数据完整性约束

**invite_codes 表：**
```sql
-- ❌ 缺少约束
max_uses INT DEFAULT 1,  -- 应该 CHECK (max_uses > 0)
used_count INT DEFAULT 0,  -- 应该 CHECK (used_count >= 0 AND used_count <= max_uses)
```

**修复：**
```sql
ALTER TABLE invite_codes

ADD CONSTRAINT chk_used_count CHECK (used_count >= 0 AND used_count <= max_uses),
ADD CONSTRAINT chk_account_expires_days CHECK (account_expires_days > 0 AND account_expires_days <= 3650);
```

## 🎯 总结和优先级

### 立即修复（Critical）

1. **时区问题** - 统一使用 UTC 时间

### 高优先级（High）

5. **微信 code 重放攻击** - 实现 code 去重
6. **数据库事务管理** - 完善异常处理

### 中优先级（Medium）

7. **激活码枚举攻击** - 统一错误信息
8. **Rate Limiting** - 添加频率限制
9. **JWT expires_at vs exp** - 取最小值
10. **使用记录在事务外** - 移入原子性函数

### 低优先级（Low）

11-13. 日志脱敏、安全头、审计日志

### 长期优化（Best Practices）

14-16. 延期功能、激活码分类、邀请奖励

**审查结论：**

代码在激活码并发控制方面做得较好（使用了事务和行锁），但在以下方面存在严重问题：
